The avatar janitor uses one persisted cleanup pass, called an epoch. The daily cron starts an epoch when the last successful pass is at least seven days old. The five-minute cron resumes an active epoch. An idle resume call reads one D1 control row and does no R2 or KV work.

An epoch has four phases: list, mark, sweep, and cleanup. Each invocation performs at most four phase steps. A list step reads at most 1,000 R2 objects. A mark step reads at most ten live entity rows, their KV documents, and linked sources within the existing depth limit of sixteen. A sweep step examines at most 100 listed objects. An invocation deletes at most 100 objects. Each cleanup step deletes at most 1,000 rows from each temporary table. Work resumes from the stored cursor rather than starting the whole scan again.

Listing must finish before marking starts. The janitor saves object keys only when their upload time is at least seven days before the epoch started. An upload that happens during a long pass cannot become eligible as that pass gets older. Listing cursors are saved so a missing or repeated cursor aborts the pass before any deletion.

Marking retains the references from both live index rows and their KV documents. A live row means that deleted_at is null, including pending and deleting entities. The index and document are independent witnesses because an interrupted write can leave either one behind. Stored local avatar overrides are also retained. Linked avatar sources are resolved from raw KV, including tombstoned source documents. A missing document, missing source, cycle, or chain past the depth limit aborts the pass. No partial mark set can authorize a sweep.

Index triggers pin both the old and new avatar URL paths during listing, marking, and sweeping. This retains references that change between invocations, including an inherited avatar whose source changes before its own mark page. The triggers run in the transaction that changes the entity index. URL paths are used so a public asset host change does not lose the object key.

This proof also relies on the avatar writers. Normal uploads, generated-image promotion, and clone copies create fresh R2 keys before publishing them. They do not restore an old unreferenced key. The epoch's upload cutoff protects the interval before the new key reaches an index. Resumable imports are the exception: they reuse a deterministic lifecycle-import key. The janitor pins all three possible import keys while their participant is pending or deleting, even when the import is older than the grace period. A new writer that publishes an old key must preserve these rules or add a coordinated publication protocol; an independent mark lookup followed by publication is insufficient.

Only a completed mark phase permits sweeping. Before each deletion batch, the janitor checks its lease and reads the current marks again. Referenced objects remain in R2. Candidate images have no durable profile reference until promotion; the seven-day grace is their retention period, as before. Promotion copies the candidate to a fresh published key.

One D1 compare-and-set lease prevents overlapping cron requests from advancing the same checkpoint. A lease lasts fifteen minutes. Each durable page write checks the token again, so a delayed request cannot replace a newer request's cursor. Repeating a deletion after an interruption is safe because R2 deletion is idempotent and avatar keys are not repurposed. A transient read or delete error leaves the phase resumable. A known incomplete mark or invalid listing moves the epoch to cleanup without sweeping.

The control row is retained for the environment lifetime. The marks, listed objects, and used cursors belong only to the active epoch. Cleanup removes them in bounded batches after success or refusal. There is no retained history of epochs. A successful cleanup writes the weekly marker; an aborted epoch does not. Checkpoints use version 1 and an unknown version stops cleanup rather than guessing or repairing stored state.

Tests use real SQLite for phase transitions, trigger behavior, and lease races, plus the Worker D1 fixture for integration. They cover a fleet above the former 2,000-entity ceiling, bounded deletion batches above the former total-delete ceiling, references changed before and after marking, old interrupted imports, missing documents, tombstoned clone sources, invalid clone chains, invalid listing cursors, and expired leases.
